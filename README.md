# Agent Failure Lab：AI Agent 可靠性测试实验室

## 1. 项目简介

Agent Failure Lab 是一个用于研究和评估 AI Agent 可靠性的工程项目。

在实际运行中，AI Agent 可能遇到工具调用失败、请求超时、异常返回、重复执行等问题。本项目计划构建一个可复现的测试环境，通过模拟不同的故障场景，观察 Agent 的执行行为，并评估不同可靠性保障策略的实际效果。

项目重点不只是让 Agent 完成任务，而是研究：

**当工具出现故障时，Agent 能否正确处理异常、恢复执行，并可靠地完成任务？**

项目目前处于开发阶段。

## 2. 项目目标

- 构建具备工具调用能力的 AI Agent。
- 实现可配置的工具故障注入机制。
- 设计可重复运行的测试场景，评估 Agent 的任务完成情况。
- 对比基础 Agent 与加入可靠性保障机制后的 Agent。
- 通过量化指标分析不同策略对 Agent 可靠性的影响。

## 4. 核心功能规划

### 4.1 工具调用与 Agent 执行

构建能够调用外部工具、接收执行结果并根据结果决定后续操作的 Agent。

### 4.2 故障注入

模拟工具调用过程中的异常情况，例如：

- 工具调用失败
- 请求超时
- 异常结果返回
- 重复执行风险

### 4.3 可靠性保障

探索并实现适用于不同故障场景的处理机制，例如重试策略、异常处理、执行状态记录与重复操作防护。

### 4.4 可靠性评估

通过统一的测试场景和评价标准，对 Agent 的运行表现进行量化分析。

计划关注的指标包括：

- 任务成功率
- 工具调用失败率
- 平均重试次数
- 故障恢复率
- 执行延迟与成本

### 4.5 对照实验
在相同测试场景下，对比基础 Agent 与增强版 Agent 的执行表现，分析可靠性策略带来的实际影响。

对比指标包括：

- 任务成功率
- 工具调用失败次数
- 平均重试次数
- 故障恢复率
- 平均执行延迟
- 模型调用成本（接入真实模型后统计）

实验结果应以可重复运行的测试数据为依据，不预先假设增强版一定优于基础版。

## 5. V1 范围与非目标

### 5.1 V1 必须实现

- 一个由模型驱动的单 Agent，支持工具调用。
- `get_order`：查询模拟订单。
- `create_ticket`：创建模拟工单。
- 使用 Pydantic 校验输入与输出。
- 使用 SQLite 保存必要的执行记录。
- 记录任务、工具调用、执行结果、异常、耗时及成本信息。
- 支持超时、限流、重复执行、越权请求、循环调用等故障场景。
- 实现权限检查、有限重试和幂等控制。
- 提供可重复运行的评测用例，目标为 30 个测试场景。
- 生成 JSON 评测报告，并提供基础演示页面。
- 使用 pytest 验证核心逻辑，并通过 GitHub Actions 自动运行测试。

### 5.2 V1 暂不实现

- 多 Agent 协作系统。
- RAG、向量数据库和知识库检索。
- Kubernetes、微服务拆分及复杂部署体系。
- 真实支付、真实客户数据或具有实际副作用的业务操作。
- React 等复杂前端。
- 不受限制的模型调用和无限重试。

以上范围用于控制项目复杂度，避免在核心可靠性机制完成前引入额外技术栈。

## 7. 开发与测试原则

1. 先完成可独立测试的确定性业务逻辑，再接入真实模型。
2. 核心测试必须能够在不配置模型 API Key 的情况下运行。
3. 模型负责提出工具调用建议，普通代码负责权限检查、参数验证和实际执行。
4. 重试必须有明确上限；可能产生副作用的操作必须考虑幂等性。
5. 通过故障注入和对照实验验证可靠性机制，而不是只展示正常执行流程。
6. 不在代码仓库中提交真实 API Key、密码或其他敏感凭据。
7. 每项功能以实际运行结果和自动化测试为验收依据。
